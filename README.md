# NEW_VOCR

مشروع استخراج ديتلات التجميع من كتالوجات PDF باستخدام خدمة Qwen الموجودة على DGX.

**ملف التشغيل الأساسي هو `run_pipeline.sh`**. الملف ينادي الأمر `as-ocr pipeline`،
والمسؤول عن مراحل التنفيذ هو `src/as_ocr/pipeline.py`. لا تحتاج تشغيل ملفات runner
المتعددة الموجودة في الأدوات القديمة.

## تجهيز المشروع مرة واحدة

فك الضغط بحيث يكون عندك فولدر `NEW_VOCR` كامل، ثم ادخل عليه من Terminal على DGX:

```bash
cd /home/domapp/Z_AiWork/NEW_VOCR
uv sync --locked --no-dev
```

استخدم ملف `.env` الحالي من مشروعك القديم للحفاظ على endpoint واسم الموديل
وهويته ومفتاح الاتصال إن وجد. انسخه إلى فولدر NEW_VOCR إذا لم يكن موجودًا فيه.
إذا لم يكن عندك ملف سابق، `.env.example` يحتوي القيم المرجعية التي تراجعها قبل التشغيل.
ملفات الاعتماديات لا تحتوي الموديل، ولا يوجد تنزيل تلقائي لأوزانه.

## تشغيل Docker ثم الـpipeline

Docker يشغّل خدمة الموديل، ويستدعي `server/start.py` تلقائيًا داخل الحاوية.
الـpipeline عميل منفصل يتواصل مع الخدمة. لو الخدمة شغالة بالفعل يمكنك استخدامها.
لتشغيل الخدمة باستخدام ملف Compose الموجود:

```bash
docker compose up -d qwen-vision
docker compose ps
```

انتظر وصول الخدمة لحالة healthy. ثم شغّل **المشروع من نفس فولدر NEW_VOCR**:

```bash
bash run_pipeline.sh '/actual/path/to/catalog.pdf'
```

هذا الأمر يعالج كل صفحات الملف. القيم الافتراضية في ملف التشغيل: Async مفعّل،
32 عامل صفحات، وحد مشترك 32 لطلبات الموديل، وقراءة الصفحة بمحرك compact.
تظل الخطوات التابعة لبعض داخل الصفحة مرتبة.

لتجربة صفحات محددة مع نتايج جديدة:

```bash
bash run_pipeline.sh '/actual/path/to/catalog.pdf' \
  --pages 1 7 10 --focused-test --fresh \
  --output-root output-test-01 --run-id test-01
```

لمراجعة خطة نفس التجربة بدون طلبات موديل أو كتابة نتائج، أضف `--dry-run`.
استخدم اسم output جديدًا في التجربة التالية. الملفات الكبيرة لا تحتاج تغيير
Docker: ميزانية الكشف تحسب تلقائيًا من عدد الصفحات والخطوات المسموحة، وتظل محدودة.

## النتيجة

CSV يحتوي **خمسة أعمدة فقط**:

```text
detail_name,profile_count,profile_id,component_name,source_page
```

- الاسم من اسم PDF بدون الامتداد: `اسم الملف_01` ثم `_02` وهكذا عبر صفحات التشغيل.
  الرقم يخص الديتلا، وليس كل صف مكوّن. عند اختيار عينة صفحات يبدأ تسلسل العينة من 01.
- العدد من خطوط إشارات المكونات المستخرجة؛ الاسم وحده أو الكود وحده يكفي.
  الاسم والكود على نفس الإشارة لا يضاعفان العدد. العدد يظهر مع المراجعة لو التغطية ناقصة.
- `profile_type` و`description` غير موجودين في CSV.
- رقم الصفحة هو صفحة PDF الأصلية بدءًا من 1، وليس الرقم المطبوع على الورقة.

تجد نتايج كل PDF داخل `output/<PDF-stem>__<source-hash>/`:

```text
details/detail_001/image.png
details/detail_001/detail.csv
details/detail_001/component_leaders_overlay.png
details/detail_001/profile_count_review.md
all_details.csv
pages/page_XXXX.md
stages/stage_XX/review.md
_internal/...
```

ملفات Markdown الناتجة للصفحات ومراجعة القص والإشارات ما زالت موجودة.

## هل ملفات tests تؤثر على Docker أو الموديل؟

لا. ملفات `tests/` لا تُشغّل تلقائيًا، ولا تُحمّل داخل خدمة الموديل، ولا يستوردها
الـpipeline. وجودها يشغل مساحة ملفات فقط؛ تشغيل pytest بنفسك يستهلك موارد الاختبارات.
أمر `uv sync --locked --no-dev` يجهز اعتماديات التشغيل دون pytest واعتماديات التطوير.

الوثائق المختصرة الباقية:

- [تفاصيل المراحل والميزانيات](docs/PIPELINE.md).
- [اختبارات النسخة والتحقق على DGX](docs/TESTING.md).

مسار أوزان الموديل وإعدادات Compose و`max-num-seqs=64` محفوظة. هذه نسخة تجهيز
واختبارات CPU؛ تشغيل Qwen وقياس الجودة والسرعة على DGX لم يحدثا في هذه الجلسة.

إضافات كتالوجات التصنيع تلحق بنهاية البرومبتات الأصلية دون حذف أي نص منها.
تضيف مراجعة علاقات التكبير والقطاعات والفصل بين بدائل Standard/HI/SI؛ تفاصيلها
في دليل المراحل. استخدم مجلد output جديدًا عند تجربة هذه النسخة.

النسخة الحالية تضيف مفاتيح شرح المكونات المرقمة، والتسمية المشتركة بين خطوط
مستقلة، ومراجع Detail الرقمية كسياق دون دمج الديتلات. يمكن ملء اسم المكوّن من
جدول في صفحة أخرى عند تطابق الكود والنطاق الموثقين، مع حفظ الصفحة والصف والخلية.
الاسم المحلي له أولوية، والتضارب يظل للمراجعة. الديتلات بلا كود وبلا اسم مدعوم
تُستبعد من التسليم النهائي وتُسجل أسبابها؛ الاسم فقط يظل صالحًا.

استخدم مجلد output جديدًا: عقد النشر أصبح 5. أمر التشغيل وإعدادات DGX كما هي.
